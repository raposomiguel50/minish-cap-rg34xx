# H700 integration: implementation, measurements and evidence limits

Miguel Raposo · Miguel's Game Dev Lab  
Technical audit and reanalysis · 7 September 2026

## Abstract

This report audits the published Minish Cap integration patches, launcher and selected archived test records. It separates source changes, historical observations, recalculated statistics and project policy. Fifteen published patches cover build configuration, handheld integration, exit handling, audio configuration and timing instrumentation/policy. A reanalysis of two historical captures reproduced their reported tick-lateness percentiles. It also retained adverse presentation-time and audio observations. The reviewed material does not establish that this integration corrected a gameplay bug in the original GBA release. Energy savings, universal compatibility and bit-for-bit reconstruction are not established. No new device session was performed for this audit.

## Method

### Scope and sources

The code reference is integration commit `90fd77a82d579de9460f2de1167a95ec264e57c3`. All 15 public patches were inspected by changed file and hunk; their Git blob identifiers were matched against copies in the supplied archive. The launcher was examined separately. Archived test outputs were read rather than generated by rerunning their original scripts. Project descriptions and approved principles were not treated as evidence that an implementation or test had occurred. Supporting files: [patch inventory](PATCH_SERIES.md), [audited launcher](https://github.com/raposomiguel50/minish-cap-rg34xx/blob/90fd77a82d579de9460f2de1167a95ec264e57c3/launcher/The%20Minish%20Cap.sh) and [reanalysis/source index](evidence/2026-09-07/reanalysis.json).

The archive contains 3,593 entries and has SHA-256 `07ae7e1be8aed80dc9494c084d3ac5bfb5b60be186f6778344bec8fb7393ca10`. Its filename, selected member paths and hashes are recorded in [reanalysis.json](evidence/2026-09-07/reanalysis.json). The archive is owner-supplied; matching hashes establishes consistency of the reviewed material, not independent authentication of the original test sessions.

### Evidence categories

**Implemented in source** means the change is visible in a specified patch or launcher. **Observed** means a specified archived output records it. **Recalculated** means this audit reproduced a statistic from archived numerical rows. **Policy** means an approved decision rule, not a completed feature. **Not established** means the reviewed evidence is insufficient for the proposed claim. A patch by itself does not prove successful execution or inclusion in every later executable.

### Timing analysis

The P11.3 and P11.4 captures were recorded on 30 August 2026. All `X` records were included; no warm-up rows or outliers were removed. Tick lateness is the recorded non-negative difference between tick closure and its scheduled deadline, in nanoseconds, converted to milliseconds. Quantiles use linear interpolation at sorted position `(n − 1)q`. Presentation-call durations use matched `PRESENT_BEGIN`/`PRESENT_END` markers by presentation sequence. Instrumentation definitions are in the [P11.1 and P11.3 patches](PATCH_SERIES.md); the calculation is in [reanalyse.py](evidence/2026-09-07/reanalyse.py).

There is **one capture per timing variant on one device**. Ticks are repeated observations within a capture, not independent experimental replications. This audit did not establish randomisation, identical gameplay sequences or a matched-scene design for this pair. It therefore reports a descriptive comparison, without a significance test, causal effect estimate or general performance guarantee.

## Results

### 1. Build and architecture integration

`P04_AARCH64_LINK_COMPLETENESS_R1.patch` adds `port/port_cloud_tops_fight.c` to the `tmc_pc` build and links EGL/GLESv2 on Linux/Android without the previous GPU-renderer condition. This is a link-completeness change; the filename does not demonstrate a correction to the original Cloud Tops encounter. `P04_FMT_PACKED_COLLISION_R1.patch` moves `fmt/format.h` before project headers. `P06_H700_CORTEX_A53_TARGET_R1.patch` adds `-march=armv8-a+simd` and `-mtune=cortex-a53` to C/C++ flags in its Linux, non-x86 condition. These are concrete build changes, not measured gameplay improvements. Each patch is linked at its audited revision in the [patch map](PATCH_SERIES.md).

The pinned foundation is EstebanPdN's `zelda-tmc-3ds` fork, whose README credits the Android port, Project Picori and zeldaret. It should not be presented as an independently created game engine or as the canonical Project Picori repository (EstebanPdN, 2026). The pin is recorded in [SOURCE_BASELINE.json](../SOURCE_BASELINE.json).

The pinned upstream commit already contains a Cloud Tops regional-flag change by EstebanPdN, conditional on the PC-port/multi-region path (EstebanPdN, 2026). The [H700 link-completeness patch](../patches/P04_AARCH64_LINK_COMPLETENESS_R1.patch) adds that source to its build; it must not appropriate the upstream change as a newly authored gameplay fix.

### 2. Exit handling: a port defect, not an original-game bug

The D2 trace, lines 302–303, records `MENU+L2`, completed subsystem-shutdown markers, `BEFORE_RETURN_0`, then `RAW_CRASH sig=11`. The D3 trace, lines 186–187, reaches `BEFORE_RG34XX__EXIT_0` after the same shutdown sequence without that crash marker. The patches propagate a quit request through waits/main loops and use `_Exit(0)` after explicit shutdown in the RG34XX seamless profile. The later final QA session records `RG34XX_GAME_EXIT_RC=0`. Sources: [diagnostic excerpts with original line numbers](evidence/2026-09-07/log_excerpts.json) and [quit-handling and shutdown patches](PATCH_SERIES.md).

This supports a targeted exit-path workaround and observed successful exit in the recorded sessions. It does **not** identify the exact failing finalizer, prove that every crash was fixed, or demonstrate a defect in the original GBA ROM. The archived `D3_EXIT_VERDICT.txt` is empty and is not used as acceptance evidence.

### 3. Presentation and controls

The P10.3 source introduces `MENU+L2` for exit and `MENU+R2` for settings; the final session reports those mappings. The P10.3.2 patch suppresses `L Settings` and its old L-button sidebar action under the seamless profile. The settings implementation is retained. These are specific integration changes, not evidence that all menus were removed. Sources: [P10.3/P10.3.2 patch map](PATCH_SERIES.md) and [session excerpts](evidence/2026-09-07/log_excerpts.json).

The launcher uses `--window_scale=3 --console-parity`. The final session reports widescreen disabled, save-state functions inert under Console-Parity, pacing locked to 59.7275 Hz and three OpenMP scanline threads. The target display is 720 × 480; 240 × 160 scaled by three yields those dimensions (ANBERNIC, n.d.). These facts do not substitute for an exhaustive pixel-by-pixel, sound or control-conformance test. The [launcher](https://github.com/raposomiguel50/minish-cap-rg34xx/blob/90fd77a82d579de9460f2de1167a95ec264e57c3/launcher/The%20Minish%20Cap.sh) and [log excerpts](evidence/2026-09-07/log_excerpts.json) identify the configuration messages; the [supplement](AUDIT_SUPPLEMENT_2026-09-07.md) addresses contradictory messages in the same session.

Approximately 119.455 Hz is a panel-mode report, not 120 FPS game logic. These measurements are neither button-to-photon latency nor proof that stutter was eliminated.

### 5. Audio: a mixed result retained in the record

At 48,000 samples/s, 1,920 and 1,600 frames correspond arithmetically to 40.000 and 33.333 ms. These are nominal buffer intervals, not measured end-to-end audio latency. The [P11.5 machine summary](evidence/2026-09-07/audio_summary.json) labels its result **`AUDIO1600_MACHINE_AUDIO_REGRESSION`**, with 172 baseline and 228 candidate logging windows.

The p95 of per-window maximum audio work fell from 30.79 to 26.53 ms, but the largest callback gap rose from 62.2 to 168.8 ms. Heuristic event counts are explicitly not literal audible-underrun counts. The later [5 September acceptance record](evidence/2026-09-07/final_acceptance.json) reports operator audio QA `OK` with the 1,600-frame configuration. That is a later human acceptance observation; it does not erase the earlier machine regression or establish inaudibility in every possible scene.

The [audio patch](../patches/P10_3_1_RG34XX_A53_AUDIO_R1.patch) also selects linear resampling for a specific RG34XX enhanced-audio branch; its `gbaAccurate` branch still selects nearest resampling. It cannot support a statement that every audio mode uses the same resampler.

### 6. Final accepted configuration and efficiency limits

The [5 September acceptance record](evidence/2026-09-07/final_acceptance.json) identifies executable SHA-256 `787ba3cb8c297ea44a0605745347fe5a6e792094f0be755b51a8200c1eadc710`, CPU ceiling 936 MHz, GPU ceiling 420 MHz, audio 1,600 frames and `TMC_RENDER_THREADS=3`. The [winner record](evidence/2026-09-07/runtime_winner.json) gives executable size 8,858,736 bytes. Its visual/audio acceptance is one operator's `OK` report from one manual session. The record also reports two automated soak runs; those are not two additional human playthroughs.

The final monitor contains 874 samples. In those samples the reported CPU/GPU ceilings and 119.455 Hz mode match the selected configuration; maximum recorded temperature is 52.6 °C. The CPU-governor ratio is 0.993135, not 1.0. The post-session display report is 60.005 Hz, and CPU/GPU maximum restoration markers report success. The pre-session CPU governor was `powersave`, while the post-session value was `ondemand`; “all machine state was restored exactly” would therefore be too broad. Sources: [monitor reanalysis](evidence/2026-09-07/reanalysis.json) and [machine summary](evidence/2026-09-07/final_machine_summary.json).

The earlier 1,416-to-936 MHz ceiling comparison is a 33.9% frequency reduction. It is distinct from the launcher's expected stock maximum of 1,512 MHz. The [P13 Stage A record](evidence/2026-09-07/stage_a_winner.json) has `energy_eligible=false` and `energy_mwh=null`. One [P13.1 comparison](evidence/2026-09-07/runtime_winner.json) records maximum temperature **5.3 °C higher** and median RSS ratio 1.003497. The evidence does not establish measured energy savings or a general temperature reduction. Reduced power/thermal demand remains the stated optimisation objective, not a measured benefit inferred from clock frequency.

The final V1 marker files dated 5 September record promotion identity, one visible game tree/menu entry and `STABLE_V1_VERIFY=PASS`. Earlier acceptance JSON deliberately says `stable_promotion=false` because it precedes that separate promotion step; both chronological states are retained. See the [marker excerpts](evidence/2026-09-07/log_excerpts.json) and [earlier acceptance JSON](evidence/2026-09-07/final_acceptance.json).

## Interpretation and limits

The evidence supports concrete H700 build/runtime work, a targeted exit workaround, curated input/presentation settings and descriptive timing results. It does **not** establish an original-GBA gameplay-bug correction, complete defect removal, lower end-to-end latency, energy savings, a full-playthrough guarantee or compatibility beyond the tested device/CFW context.

Native game-logic execution should not be described as eliminating all graphics/audio modelling or all software layers. The reviewed path includes Linux, SDL integration and software reproduction of GBA presentation/audio behaviour. No controlled native-versus-emulator performance comparison was identified in this audit. The [patch inventory](PATCH_SERIES.md), [launcher](https://github.com/raposomiguel50/minish-cap-rg34xx/blob/90fd77a82d579de9460f2de1167a95ec264e57c3/launcher/The%20Minish%20Cap.sh) and [recorded configuration](evidence/2026-09-07/final_acceptance.json) define the inspected scope.

Approved restoration policy allows future justified bug corrections. Such a policy is not a result and is not a claim that a specific original defect was fixed. Each future result needs its own reproduction case, change, build identity and before/after validation.

The public patch archive is not a complete final build tree. The private executable was not rebuilt or executed during this audit. Original traces and private materials remain in the owner-supplied archive; selected machine records, hashes and the analysis script are published separately. This is a technical audit with direct project-evidence links and APA-style references for external sources, not peer review or an independent hardware replication.
